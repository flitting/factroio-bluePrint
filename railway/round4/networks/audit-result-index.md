## 计数与等价判据

### 完成案例与设计成功分开

`exit_code == 0` 加最终结果足以表示一次完整的原生实验，不能单独表示所有 OD 获得服务、无饥饿、无损伤或高吞吐。一个完整跑完但某 OD 不通行的失败候选，仍是搜索证据，应计为“完成测试”，不能列为“验证通过方案”。失败建造、超时、无最终结果、被环境中断的半截输出均不在完成案例计数内。

索引的 `*/request.json` 只扫实验一级目录，因此没有重复计算 `interrupted-attempts/` 中的旧尝试。Dense307 环境中断后，重新执行的是同一个冻结逻辑案例，从 tick 0 重跑；旧日志归档不会增加案例数。

本表不包括单独的建造/静态路径审计、API 探针、CPU 重复基准或图纸导入检查。若报告另行统计这些运行，应分层报告，避免把“引擎启动次数”“流量案例数”“配置数”“几何数”相加成同一项。

## 主指标逻辑复核

### 严格半开测量窗正确

对于测量窗 `[a,b)`，当前主指标使用：

`完成数 = 窗内入场数 + a 时刻在途数 − b 时刻在途数`

其中“时刻 t 在途”为 `entry_tick < t <= complete_tick`，未完成请求的结束时间视为窗后。这个约定与 `[a,b)` 的入场/完成事件计数一致：恰好在 a 发生的事件属于测量窗；恰好在 b 发生的事件不属于测量窗。所有完成记录的库存恒等式都通过独立复算。

长短尾的样本尤其说明必须保留该诊断。两者的完成量差异可能来自起止库存变化，并不能单由有限窗口的出场计数解释成容量提高。本 agent 的两个 formal 窗已经在局部报告记录该问题。

### FIFO、需求配对和跨组均值

原主脚本只验证已经进入的车辆 ID 递增，理论上可能漏掉“跳过中间请求”的情况。主线现已改为严格验证每来源完整请求序列的前缀，所有已完成数据也通过更强的独立检查。

配对比较哈希包含 `(id, origin, destination, arrival_tick)` 完整请求序列，并检查相同 seed、银行规模、预热窗、测量窗、协议源、共同交通设置、引擎身份。selection 与 fresh holdout 分开建立均值，没有把 bank150 的 1+3 分钟组与 bank240 的 2+4 分钟组混在一起。相对提升使用同一组的均值之比；另列每 seed 差异，没有把百分点和列车率混用。

完成队列延迟只统计窗内已完成车辆，代码和输出均明确标为 completed-cohort。不能把这个值称为所有请求的平均等待时间。P95 使用 nearest-rank；局部早期报告曾使用线性插值 P95，两者必须注明方法、不可悄悄混用。

OD 最大无完成间隔包含被测量窗边界截断的区间，变量名已有 censored 提示。单凭该值不能判“饥饿”，还需同时观察对应 OD 是否仍有待服务请求。有限回放中未死锁、封路后排空和已选路径 DAG，均不构成任意需求下的无死锁证明。

### 发布证据绑定

主线已采纳以下加强：导出蓝图必须匹配冻结 SHA；原生导入检查绑定实际图纸簿 request；W 封路检查明确两个 ID × open/closed 的四例；全出口封闭恢复检查明确预定的 Trident 单例、seed17、320 请求全部完成并退休且零损伤，避免对空列表调用 `all()` 而误通过。

审计还实际复现过补丁引入的一个断言回归：原生输出的 `raw.config` 不包含大字段 `blueprint`，而请求 `config` 包含，二者不能直接相等。应比较去掉 `blueprint` 的请求配置，并另用冻结/受测输入哈希绑定图纸；已立即反馈主线，并确认修正已经合并。

`aggregate` 目前仍按 ID 汇总传入数组，而不是自身强制检查所有分组设置；因此它作为通用函数不能防止调用者混入别组。但本轮实际 selection/holdout 调用、冻结请求及独立配置核验没有混组。若继续复用该函数，建议在函数内增加共同设置/源/引擎签名一致的断言，并在发布门槛明确 selection 的预期六个 ID。

最终报告可报告“完成 136 次原生流量案例，覆盖 95 个不同实体配置、54 个不同轨道几何”。五目录分解为 126 个常规流量案例、4 个 W 封路/开放配对案例、1 个全出口封闭恢复案例、3 个电路批次案例、2 个间距诊断案例。剩余一项是原始 spacing4 尝试的原生施工失败，明确排除；没有仍在运行的流量案例。不要把该句写成 95 个成功解或 54 种全新抽象拓扑。截短尾部、缓存长度、分流/汇流顺序、空间嵌入和信号策略同时变化的候选，应整体比较，不单独归因于某一个机制。
